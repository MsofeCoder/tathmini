MOROGORO VOCATIONAL TEACHERS' TRAINING COLLEGE

Tathmini — from prototype to production

Technical architecture, security posture and delivery plan for the Digital Assessment Sheet (TP & IPT)
THE RECOMMENDATION IN ONE PARAGRAPH

Build Tathmini as a Next.js progressive web app on a Supabase Postgres backend, with the assessment record protected by database-level row security and an append-only audit log rather than by application code. Every mark is captured offline in IndexedDB and released to the server through a single durable outbox; the server, not the phone, is the authority on totals, grades and the competency verdict. Results are immutable once both assessors have submitted. The database is backed up automatically every night to encrypted storage the College controls, with the status of that backup visible on the Super Admin panel and a restore that has actually been rehearsed. Nothing in this stack is exotic: it is chosen so that a competent Tanzanian developer can maintain it after handover, and so that an auditor can be shown exactly who marked what, when, and from where.

2 · The stack, and what I rejected

A stack is a set of liabilities you agree to maintain. Each choice below is followed by the alternative I turned down, because in five years the College will be asked why — and the answer should already be written down.

Layer Choice Why this one Rejected, and why
Application Next.js 15 (App Router), React 19, TypeScript strict One codebase serves the PWA and the server routes that must hold the marking rules. Server Components keep the phone bundle small. React Native / Flutter — an app store release cycle the College cannot control, and no benefit here: the device APIs we need are all on the web.
Styling Tailwind CSS v4 + a small set of Radix primitives Radix gives correct focus and keyboard behaviour on dialogs and menus, which is where accessibility is usually lost. Tailwind keeps the shipped CSS near-zero. MUI / Chakra — 200 KB+ of component framework on a phone that is already struggling.
Offline store Dexie 4 over IndexedDB, with a typed outbox Mature, small, well understood. The outbox pattern is boring on purpose: one queue, one worker, idempotent keys. PouchDB / RxDB sync — bidirectional replication invites conflict resolution we do not want anywhere near a grade.
Service worker Serwist The maintained successor to Workbox with first-class App Router support; precache, runtime caching and Background Sync in one config. next-pwa — unmaintained; hand-written SW — the single easiest way to ship an app that will not update.
Database & auth Supabase — Postgres 16, Auth, Storage, Realtime Row-level security lets the marking rules live in the database, where no client bug can bypass them. It is plain Postgres, so the College is never locked in. Firebase — proprietary query model, weak reporting, painful exports; bare VPS + Express — the College would own patching, backups and TLS forever.
Data access Drizzle ORM for migrations and server queries SQL-shaped, typed, and it produces migration files a DBA can read and review before they run against results. Prisma — heavier runtime, and its migration diffing is harder to audit line by line.
Validation Zod schemas shared by client and server One definition of a valid assessment. The phone uses it for guidance; the server uses the same file as the gate. Client-only checks — the classic way marks arrive that no form could have produced.
PDF Server-side Chromium render of the same HTML form The VETA sheet is a dense table; HTML reproduces it faithfully, and rendering it once on the server makes every copy byte-identical. Browser print on the phone — margins, fonts and page breaks differ per handset.
Notifications Beem Africa / Africa's Talking (SMS), Brevo (e-mail) Local gateways with registered Tanzanian sender IDs deliver reliably to Vodacom, Airtel, Tigo and Halotel; an international aggregator often does not. Twilio — priced in USD per message with poorer local routing; WhatsApp Business API — template approval and per-conversation fees, unnecessary while wa.me costs nothing.
Hosting Vercel (app) + Supabase in af-south-1 Cape Town The nearest region to Morogoro — roughly 40–70 ms instead of 200 ms+ via Europe, which is felt on every save. EU region — slower and raises avoidable data-residency questions.
Testing Vitest (rules), Playwright (offline journeys), pgTAP (RLS) pgTAP is the one that matters: it proves in CI that a Coordinator token genuinely cannot write a mark. Manual testing only — grading rules silently drift with every change.
Monitoring Sentry (errors), Supabase logs, Better Stack uptime A supervisor in the field will not file a bug report. The system has to report its own failures. Nothing — the default, and the reason pilots quietly fail.

3 · Security architecture

Tathmini holds the record that decides whether a person qualifies to teach. The threat is not a stranger on the internet; it is a plausible internal edit that nobody can later disprove. The design answers that first.

IDENTITY
  • Accounts created by Super Admin only; no public sign-up route exists in the codebase.
  • Argon2id password hashing; forced change on first sign-in; 12-character minimum with a blocked-common-password list.
  • TOTP second factor mandatory for both Super Admin accounts, optional for Coordinator.
  • Sessions are httpOnly, Secure, SameSite=Lax cookies; 12-hour supervisor lifetime, 1-hour admin idle timeout.
  • Sign-out revokes server-side, and wipes the local Dexie cache of any trainee data.
AUTHORISATION
  • RLS enabled on every table; the default is deny.
  • Supervisor: read and write only their own assessor slot, only for trainees on their assigned route.
  • Coordinator: SELECT and export. No INSERT, UPDATE or DELETE grant exists for that role.
  • Super Admin: full access, but every write is attributed and logged.
  • The service-role key never reaches the browser and is stored only as a server environment secret.
RECORD INTEGRITY
  • Submitted marks are append-only: no UPDATE grant on assessment_marks for any role.
  • Corrections create a superseding revision; the original stays visible with its reason.
  • Totals, grade, GPA and the competency verdict are computed in Postgres, not accepted from the client.
  • Each generated PDF is SHA-256 hashed and the hash stored with the result, so tampering is detectable.
  • Append-only audit log with a hash chain: actor, action, target, timestamp, device, IP.
TRANSPORT & DATA
  • TLS 1.3 everywhere with HSTS; the app refuses to run over plain HTTP.
  • AES-256 encryption at rest for database and storage.
  • Strict Content-Security-Policy, no inline scripts, no third-party analytics.
  • Report files served only through short-lived signed URLs (5 minutes), never public paths.
  • Rate limiting on sign-in and export routes; lockout after five failed attempts.
  • Trainee phone numbers and e-mail addresses are never written to application logs.
THE RULE I WOULD NOT NEGOTIATE

Authorisation belongs in the database, not in the interface. Hiding a button is a courtesy to the user; a row-level security policy is what stops the write. Every prototype I have seen fail an audit failed because those two were confused. If the College later asks for a feature that can only work by relaxing RLS, the honest answer is that the feature needs redesigning — not the policy.

5 · Daily automatic backup and recovery

A backup nobody has restored is a rumour. This is specified as a working capability with a visible status, not a checkbox in a hosting console.

WHAT RUNS, AND WHEN
  • 02:00 EAT daily — full logical dump of the database plus the report-file manifest, compressed and encrypted with age before it leaves the server.
  • Continuous — Supabase point-in-time recovery for the last 7 days, so a mistake at 14:10 can be undone to 14:09.
  • Weekly — a copy written to a second provider in a different account, so a compromised console cannot delete every copy.
  • Monthly — an archive snapshot retained for 24 months for VETA audit.
  • Quarterly — an automated restore into a scratch database that verifies row counts and checksums, then reports pass or fail.
WHAT THE SUPER ADMIN SEES
  • Last successful backup, its size, duration and checksum — green, amber after 26 hours, red after 48.
  • A 30-day calendar of backup outcomes, so a silent run of failures is impossible to miss.
  • Download of any retained backup, gated behind re-authentication and TOTP, and itself written to the audit log.
  • "Run backup now" before any risky operation.
  • Result of the last restore rehearsal, with its date.
  • E-mail alert to both Super Admins the moment a backup fails.
Scenario Recovery point (RPO) Recovery time (RTO) Mechanism
A record deleted or edited in errorUnder 1 minuteMinutesPoint-in-time recovery; usually the audit log alone is enough
A bad migration corrupts a tableUnder 1 minuteUnder 1 hourPITR to the moment before the migration ran
Total loss of the hosting accountUp to 24 hoursUnder 8 hoursRestore the nightly encrypted dump onto a fresh project
A supervisor's phone is lost mid-routeUnsubmitted drafts onlyImmediateEverything submitted is already server-side; the route is reassigned

The encryption key for the nightly dumps is held by the College, not by the developer, and is kept in two sealed copies in the Principal's office and with the ICT Unit. A backup the developer alone can decrypt is not a College backup.

The device that matters is a mid-range Android on 3G, held in one hand, in a noisy workshop, sometimes in bright sun. Every budget below is measured on that device in CI, not on a laptop.

Beyond the numbers, four things carry the field experience: touch targets never below 44 px and score buttons deliberately larger; a contrast ratio of at least 7:1 so the screen survives direct sunlight; the entire assessment reachable one-handed with the thumb; and no destructive action without an explicit confirmation, because a mis-tap in a workshop is not the user's fault. Swahili is a first-class interface language, not a translation layer bolted on at the end — the notification templates already are, and the interface strings should follow before pilot.

7 · Delivery plan

Fourteen weeks to a supervised pilot, twenty to institutional handover. The sequence is deliberate: the record-keeping guarantees are built before the features that depend on them, because retrofitting an audit trail is how projects lose a term.

Phase Weeks Delivered Gate before the next phase starts
0 1–2 Repository, CI, environments, Supabase project in Cape Town, schema and RLS policies, seeded criteria from the verbatim VETA forms. pgTAP proves a Coordinator token cannot write a mark.
1 3–6 Supervisor PWA: sign-in, route, offline marking for all three instruments, gating, auto-comments, draft recovery, outbox sync. A complete assessment survives airplane mode, a force-quit and a reboot.
2 7–9 Two-assessor independence, server-side scoring, PDF generation matching the VETA sheet, e-mail delivery, notification history. Two supervisors mark one trainee; neither sees the other; the average is correct to the decimal.
3 10–12 Admin console: accounts, routes, reassignment approvals, overrides with reasons, Excel export, audit log viewer, backup panel. A restore rehearsal completes and the panel reports it.
4 13–14 Hardening, penetration test, accessibility audit, Swahili interface strings, supervisor training, pilot on one route. No high or critical finding open; pilot supervisors sign off.
5 15–20 Full cohort rollout, parallel paper run for one term, handover documentation, source and credential transfer to the College. Paper and digital results agree for every trainee in the parallel run.

10 · Decisions needed from the College before Phase 0

Seven answers. Each one blocks something concrete, and each is a decision only the College can make.

1Does the data have to remain in Tanzania?If yes, self-hosted Supabase on a local provider replaces the managed service and adds roughly three weeks plus an ICT operations burden.
2Who are the three e-mail recipients of every result?Named roles, not individuals, so the list survives staff changes.
3May a Super Admin override a submitted mark at all?My recommendation is yes, with a mandatory reason and full visibility — but the Academic Board should decide, not the developer.
4What happens when the two assessors differ widely?A threshold — say 15 marks — could flag the pair for Coordinator review before the average is published. Currently the system just averages.
5Should the trainee receive their own result automatically?Affects whether trainees need accounts at all, and what a trainee may see.
6GPS stamping at submission — on or off?It answers "did the supervisor visit?" but it also monitors staff. A governance decision, not a technical one.
7How long must results be retained?I have assumed 24 months of archives for VETA audit. Confirm against College policy.
WHAT I WOULD DO FIRST, IF ONLY ONE THING

Build the schema, the row-level security policies and the pgTAP tests that prove them — before a single screen is written. It is two weeks of work with nothing to demonstrate at the end, which is exactly why it gets skipped, and exactly why systems like this one fail their first audit. The interface can be rebuilt in a month. A record nobody can trust cannot be repaired at all.
